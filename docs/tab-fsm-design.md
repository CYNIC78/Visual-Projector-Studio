# Галерея как конечный автомат — дизайн (статус: КАРТА + ПРЕДЛОЖЕНИЯ, решение за владельцем)

Дата: 2026-07-29. Инициатор: владелец (после консультации с Gemini, который
подтвердил: система категорий/табов + динамический коллаж — самополучившийся
конечный автомат; табы могут быть чем угодно: инвентарь, позы, боевая сцена).
Установка владельца: «не торопиться, осмотреться и внедрять действительно
полезные фичи, укрепляющие систему и делающие её гибче и понятнее для модели».

## 1. Тезис: автомат уже на 80% построен

Формальное соответствие (проверено рекогносцировкой кода):

| FSM | У нас | Где в коде |
|---|---|---|
| Состояние | открытый таб (эксклюзивно!) | соло-свип v17, `executeCommand` |
| Вложенные состояния | категории (паки) поверх табов | galleryData.categories |
| Алфавит переходов | грамматика `[TAB:open/close]`, `[CAT:…]` | v17 parseDirBody |
| Исполнитель переходов | МОДЕЛЬ (бесплатный, «туповатый, но растёт») | текст v17 → тул v25 |
| Наблюдение состояния | динамический коллаж (витрина комнаты) | v18–v23 → зрение v25 |
| Меню переходов | «Closed scenes» в манифесте/наблюдении | v12 manifest, v24/v25 |
| Скрытые состояния | `locked` — 🔒 «Hidden from LLM» | gallery-hierarchy, 3 состояния |
| Правила/законы состояния | поле **`desc` на табе и категории** — с редактором «📝 Изменить описание» и честной подписью «Описание видно модели, когда категория/таб свернут» | gallery-hierarchy.js:160 |

Ключевой поворот истории: **соло-свип v17** сделал открытый таб эксклюзивным —
именно тогда «папки с картинками» стали состояниями. Всё остальное (зрение,
тул, меню) — это нервная система автомата, которую мы достроили, не подозревая.

## 2. Три дыры в готовом каркасе

1. **Описания не в точке решения.** `desc` ездит в манифесте (каждый запрос, и
   для свёрнутых, и для открытых табов — vp-templates.js:269/290/294), но
   навигационные фидбеки v24 (buildSceneTransitionObservation) и v25
   (scene_navigate result) перечисляют закрытые сцены **только именами**. Модель
   выбирает дверь вслепую — по имени, не по смыслу.
2. **«Правила комнаты» без въездного повтора.** `desc` — единственное поле
   закона. При входе (момент свежего коллажа v25 — высшая точка внимания)
   модель получает теги и картинку, но не закон комнаты рядом с ними.
3. **Нет дверей.** Граф полный: из любого состояния можно попасть в любое
   (меню = все свёрнутые табы). Для сюжетных структур, прогрессии, «запертых
   дверей» нужна опциональная география.

## 3. Принципы дальнейшего строительства (предлагаю)

- **Модель — исполнитель, текст — закон.** Автомат мягкий: правила читает и
  исполняет модель (наша философия «бесплатного FSM, который умнеет»).
  Машинное принуждение — только в точках честности (дверь не открылась —
  честно сказать «нет прохода», а не соврать «ты вошёл»).
- **Данные живут на табе** (desc, exits), не в отдельных манифестах —
  никакого шторма подсказок (см. tools-management-audit.md).
- **Полная графность по умолчанию.** Всё новое — опционально; пустое поле =
  поведение сегодняшнего дня. Обратная совместимость святая.
- **Диета соблюдается:** каждая прибавка в контекст — только в навигационные
  туры (tool result / observation), не в перманентный манифест.

## 4. Шаг 1 — «Смысловое меню выходов» (малая кровь, мгновенный эффект)

- `buildSceneTransitionObservation` (v24): `Closed scenes` →
  `Имя — desc (80-кап)` вместо голых имён.
- `scene_navigate` (v25): `closedScenes: [{name, desc}]`; `focusScene.desc` —
  закон комнаты повторяется В МОМЕНТ ВХОДА рядом со свежим коллажем;
  pack-переход несёт `desc` категории.
- Токены: ~60–80 зн × число закрытых табов, только в туры навигации. Диета OK.
- Код: два точечных диффа (session-manifests.js, vp-core-tools.js) + смоуки.

## 5. Шаг 2 — «Двери» (опциональная география переходов)

- Поле `tab.exits: string[]` (имена табов; пустое/нет = полный граф, как ныне).
- UI: пункт контекстного меню таба «🚪 Проходы…» (showPrompt, comma-список —
  рядом с «📝 Изменить описание», паттерн тот же).
- **Чокпоинт честности:** `TabsManager.executeCommand` — если у ОТКРЫТОГО таба
  задан `exits` и цель не в списке → мир не меняется, тост «🚪 из «X» нет
  прохода в «Y»», возврат мисс-результата. Ручные клики сайдбара чокпоинт не
  проходят (владелец = бог, как ныне и задокументировано).
- **Фидбек честности:** наблюдение/тул-результат при блоке сообщает
  «прохода нет; отсюда ведут: A, B» и озвучивает меню ТОЛЬКО легальных выходов
  (когда exits задан). `scene_navigate` чекает дверь ДО исполнения; текстовая
  ветка v24 получает честность через пост-проверку состояния в observation
  (open-note: если таб не открылся — «passage blocked», не «you enter»).
- Токены: ноль в обычных турах; меню даже худеет при заданной географии.

## 6. Горизонты (зафиксировать, НЕ строить сейчас)

- **Типизированные табы** (`kind: scene|inventory|poses|combat`): у инвентаря —
  автоподсказка «используй [IMG] только из открытого набора»; у боевой сцены —
  свой lifecycle/правила хода. Это уже «платы расширения» автомата.
- **State-bound манифесты:** закон комнаты пинится, пока таб открыт (TTL,
  привязанное к состоянию, не к турам). Мощно, но риск шторма — ждёт вердикта.
- **Причины запрета на дверях** («в подвал — только с ключом»): поле reason на
  exit-запись. Только по запросу реальных сценариев.
- **Редактор графа:** визуальная карта дверей в галерее. Красиво, дорого, поздно.

## 7. Предлагаемый порядок

Шаг 1 (v27) — смысловые меню: день работы, риска ноль, модель СРАЗУ начинает
выбирать двери по смыслу (существующие описания наконец доезжают до точки
решения). Шаг 2 (v28) — двери: опциональная география поверх. Горизонты —
по реальным сценариям владельца.

## 8. РЕШЕНИЕ ВЛАДЕЛЬЦА 2.0 (2026-07-29) — «закон активного состояния»

Коррекция курса владельцем: «двери» были импровизацией — сняты с плана.
Центр внимания: **управление состоянием и условиями АКТИВНОГО таба**. Идея
владельца (принята): вшить правила в сам коллаж / в текстовый блок рядом с
коллажем после системного промпта; для ввода — новое поле в интерфейсе.

**Развилка каналов и выбор (ask_user):** текст-спутник коллажа (выбран),
краска на картинке (отложена как горизонт: даунскейл ~1024px + 12b vision =
негарантированная читаемость; при желании — пилот с крупным баннером).

**Два поля, две аудитории (зафиксировано):**
- `desc` (уже был) — витрина/приглашение, видно модели у свёрнутого;
- **`rules` (новое)** — закон активного состояния: читается моделью, пока
  таб на витрине, и в момент входа. Редактор в контекстном меню таба
  («⚖️ Правила таба»), хранится в galleryData.

**Каналы доставки (реализовано в v27):**
1. **Текст-спутник коллажа** — коллаж-сообщение (high-attention zone сразу
   после системного) получает text-part `[GALLERY VIEW — RULES OF THE
   DISPLAYED SCENES]` со списком законов помеченных табов (кап 300 зн/таб,
   900 суммарно). Нет законов на витрине — сообщение остаётся чисто
   картиночным (нулевой дифф, нулевые токены). Собирает
   `VP_TEMPLATES.buildCollageRulesNote(galleryData)`.
2. **Повтор в момент входа** — наблюдение v24 (`Rules of "X" (law of this
   scene)`) и `focusScene.rules` тулa scene_navigate (кап 300).
3. **Манифест-fallback** — строка `[RULES: …]` у открытого таба, ТОЛЬКО
   когда витрина неактивна. Exclusive-or со спутником: двойной оплаты нет.

**Диета соблюдена:** перманентная прибавка — только фактически введённые
правила (поле пустое = ноль). Горизонты (desc в меню переходов, pack-rules,
краска-баннер, типизированные табы) остаются на карте §6.

*Смежные документы: tab-attention-design.md (v17, соло/FSM-грамматика),
agentic-loop-design.md (v24/v25, исполнение и зрение),
tools-management-audit.md (дисциплина токенов).*

## 9. РАЗВИЛКА 2 (2026-07-29, вечер) — «интерфейс внутри таба»: stat-блоки vs games.js
**СТАТУС: АНАЛИЗ ПРОВЕДЁН, решение за владельцем.**

Триггер — идея владельца: раз галерея стала визуальным FSM, почему бы в поле
`rules` не держать машиночитаемый блок рядом с законом для модели — и при
входе в таб «бой» рисовать/менять интерфейс (HP/стамина противников). Вопрос
владельца: насколько это удобно менеджить в сравнении с games.js.

### 9.1 Разведка (факты, снятые с кода)
- `projector-games.js` — НЕ план, а ПОСТРОЕННЫЙ фундамент (1441 строка):
  жизненный цикл модулей (mount/unmount/activate/deactivate/
  buildPromptContext/startActivity/autoResolveActivity), полноэкранный
  overlay, брокер активностей с тегами `[ACTIVITY_*]` (модель предлагает —
  юзеру тост Play/Auto/Decline), `[SCENE EVENT]` в сессию, доверенный
  `makeApi`: пер-игровое состояние (getState/setState/log), ВНЕОЧЕРЕДНЫЕ
  вызовы модели (`llmComplete`, `llmJson` с валидацией формы и fallback),
  VP_HUB, субтитры; панель 🎮 в shell; prompt-provider активной игры.
  Игры хранятся в БД (games index), загружаются как модули-код.
- `vp-interactive.js` — сенсорный слой: регионы на ассетах, единый тег
  `[TOUCH:...]` в обе стороны (юзер и модель), принцип анти-дрейфа:
  «не два параллельных формата, которые могут разъехаться» — семантику
  жестов отдали игре/FSM. Этот же принцип обязателен для любого
  stat-слоя: он НЕ должен стать вторым, параллельным games.js.
- Экспорт/импорт галереи несёт дерево (tabs с полями) — значит правила и
  любой stat-блок едут вместе с паком бесплатно. Игры — отдельные записи
  БД, перенос сложнее.

### 9.2 Суть развилки: «кто процессор изменений состояния»
Поле `rules` с v27 уже ЗАКОН для модели. Новый вопрос не «где хранить код»,
а кто ВЫЧИСЛЯЕТ дельты (hp−3):
- В games.js процессор = детерминированный JS (работает даже с тупой
  моделью; можно спросить модель внеочередным llmJson-арбитром и не платить
  контекстом основного чата).
- В stat-блоке процессор = сама модель через узкий тег `[STAT:id:±N]`
  (линейка грамматик уже есть: `[TAB:open:X]`, `[TOUCH:...]`, `[ACTIVITY_*]`)
  + клики юзера ±; проектор валидирует/клампит рельсы (min/max) и эхом
  отбрасывает `[SCENE EVENT]` в контекст — тот же action→perception цикл,
  что освящён в v25.

### 9.3 Инженерная граница (не пересекать)
Произвольный JS внутри `rules` — НЕТ: нет песочницы, опечатка ломает
проектор, вслепую это не отладить и не покрыть смоуками. Только
декларативный блок в явном заборе (напр. fenced ` ```stats `, линейная
грамматика `bar hp "Гоблин" 14/20` / `counter arrows 12` / `badge ...`),
который ПАРСИТСЯ, а не исполняется. Битый блок = тост и игнор, не крах.

### 9.4 Взвешивание «менеджить»
- Авторство: stat-блок — дизайнер правит текст в ⚖️-редакторе, без кода;
  игра-модуль — пишется кодом (мной), автономии владельца нет.
- Надёжность: игра — детерминизм; stat-блок — модель как CPU (12b может
  забыть эмитить теги); смягчение: рельсы-клампы, эхо в контекст, клики ±,
  философия владельца «модели умнеют — время работает на нас».
- Контекст: у обоих (rules-спутник v27 с капами; prompt-provider игры).
- UI-свобода: игра — канвас/анимации/таймеры; stat-блок — малый словарь
  (полоски/счётчики/бейджи) = 80% настольных нужд, не аркада.
- Распространение: stat-блок едет с экспортом пака; игра — отдельная запись.
- Вслепую-безопасность: парсер+рендер+исполнитель ≈ 300–400 строк одним
  спутником, полностью смоукябельно; JS-в-rules — нет.
- Дрейф/крип: закон границы — «понадобился if/таймер/анимация/llmJson —
  это игровой модуль», stat-словарь не растит.

### 9.5 Вердикт (рекомендация)
Системы НЕ конкуренты — это слои: FSM/коллаж отвечает «где мы и каков тут
закон», games.js — «кто считает тяжёлую механику». Недостающий листовой слой
— stat-блоки (простая арифметика HP/стамины/ресурсов прямо в состоянии таба,
видимая и юзеру, и модели). Шов горизонта: таб может однажды ССЫЛАТЬСЯ на
игру-модуль (`game: id` в rules) — «таб = дверь в аркаду»; строить только по
явному запросу. Краска баров на сам коллаж отложена по аргументу v27
(даунскейл+12b vision = нечитаемо); модель узнаёт об изменениях через
`[SCENE EVENT]`-эхо, а не глазами.

## 10. НАХОДКА (2026-07-29, поздний вечер) — вариации ассетов: статус концепта
**СТАТУС: РАЗВЕДКА ПРОВЕДЕНА, строительство не начато (та же пауза, что §9.6).**

Вопрос владельца: «мы хотели или даже реализовали вариации ассетов; в студии
табы переименовали в вариации — попал ли тот билд в текущий и работает ли?»

### 10.1 Что ВНЕДРЕНО (производственная половина — студия)
- `js/nodes/core_nodes/prompt.js` v2 «Prompt Variants»: Prompt-нода живёт на
  `data.variants[]` + `activeVariantId`; авто-миграции старых схем
  (positive/negative → variants; tabs → variants) СТИРАЮТ старые поля;
  `Graph.produce()` вариант-aware (`process()` читает `getActiveVariant()`).
- LLM-тул `configure_prompt_studio` (диета v26) пишет новую схему variants.
- **Баг, найденный разведкой и починенный в v28:** массовая генерация
  «▶▶ All» читала стёртые миграцией `data.tabs` → была мертва (вечный тост
  `No prompt tabs found`); читает variants (fallback legacy tabs). Заодно:
  `debugReferences` отчитывается по `activeVariantId`; тултип кнопки —
  «Generate all variants» (ровно тот ренейм, что помнит владелец).

### 10.2 Что НЕ ПОСТРОЕНО (галерейная/модельная половина — ни в одном слое)
Разведка по storage / gallery / collage / templates / manifests / tools /
session: концепта «базовые ассеты + стандартизованные вариации» НЕТ. Т.е.:
- нет полей `base`/`variantOf` на ассете и стандартизации вариаций
  (эмоции) внутри таба/категории;
- в коллаж не умеем отправлять ТОЛЬКО базы;
- модель нигде не обучается соглашению имён (emily_standing →
  emily_standing_happy);
- модель не может ВЫБРАТЬ вариацию.
Идея идеально ложится на философию проекта: масштабирование 10 → 100
ассетов в табе без 10× цены по токенам; простое текстовое соглашение имён
(простая грамматика = самоценность для слабых локальных моделей);
эксклюзивность витрины уже есть. Кандидатные швы (НЕ строить без явного
решения владельца; та же дисциплина, что stat-блоки §9.6): поле
`variantOf` на ассете; фильтр коллажа «только базы»; строка-учебник в
манифесте или законе таба (v27-канал); тег выбора `[VAR:base:emotion]` в
линейку грамматик v17/v25. Решение — после домашних тестов v25–v28.

## 11. СВЯЗЬ (2026-07-31) — стратегия визуальной композиции

Решения по слоям/прозрачности/фонам-референсам и формулировка «прицепа»
вынесены в отдельный документ: **`docs/visual-composition-strategy.md`**.

Кратко: рантайм-композитинг (альфа, слои, позиционирование) НЕ строим —
композит переносится на этап генерации через множественные референсы
Prompt-ноды (механика уже есть в коде). Мизансцену дают три задела без
прозрачности: прицеп (кто в кадре) · вариации (в каком состоянии) ·
фон таба как референс (где происходит).
